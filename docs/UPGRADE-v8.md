# v8 — 상용화 업그레이드 (2026-08-12)

목표: "난이도·중독성·실제 학습"을 상용 수준으로. 전부 **실측 전후 수치**로 판정했다.

## 0. 한 줄 요약

이 게임의 가장 큰 결함은 **수학을 잘해도 게임 결과가 달라지지 않는다**는 것이었다.
정답률 60%와 100%가 전 학년에서 똑같이 59웨이브에서 죽었다. 학습 게임인데 게임 안에
공부할 이유가 구조적으로 없었다. v8은 그걸 고치는 작업이다.

## 1. 학습 → 결과 연결 (핵심)

### 진단 (tools/accuracy-sweep.mjs, 학년×정답률 격자, 시드 5개 중앙값)

```
v7 4학년  30%→15  40%→15  50%→24  60%→59  70%→59  80%→59  90%→59  100%→59
                                    └────────── 차이 0 ──────────┘
```

원인은 화력 상한이다. 타워 성장(레벨10 × 각성3 × 타워수)이 웨이브 43 근처에서
포화하고 — 95%봇 DPS가 wave43~60 내내 27,496으로 고정 — 그 뒤로는 몬스터 HP만
지수로 오른다. 상한 도달 시점이 정답률과 거의 무관하니, 상한 이후 15여 웨이브가
정답률 차이를 전부 지웠다.

### 처방 — 정답이 **상한 자체**를 올리게 한다

| 장치 | 내용 |
|---|---|
| 집중력(Focus) | 정답 +1 · 오답 −2 · 0~40. 모든 타워 피해 ×(1 + 0.022×집중력), 만점 ×1.88 |
| 각성 상한 | 3 → 6 (비용 20배×2ⁿ이라 정답 보상으로 경제를 굴린 아이만 도달) |
| 정답 보상 | 웨이브 계수 10 → 22 |
| 처치 골드 | 배율 1+w/12 → 1+w/20 |

**설계 원칙 — 못하는 아이를 더 때리지 않는다.** 집중력은 0 아래로 안 내려가고,
0이면 기존 게임과 완전히 동일하다. 오답 페널티(성 체력)는 손대지 않았다.
격차는 "벌"이 아니라 "상"으로 만든다. 오답을 정답보다 무겁게(−2 vs +1) 둬서
4지선다 찍기(25%)로는 한 점도 안 쌓인다.

### 결과

```
v8 4학년  30%→15  40%→24  50%→55  60%→59  70%→59  80%→63  90%→71  100%→71
                                    └────────── 차이 12 ─────────┘
```

- 못하는 구간(30·40%)은 그대로거나 나아졌다 — 하드월을 만들지 않았다
- 100%도 71웨이브에서 죽는다 — "언젠가는 뚫린다"는 서바이벌 구조 유지

⚠️ 스윕은 **공통난수(common random numbers)** 로 돌린다. 시드에 정답률을 섞으면
정답률 칸마다 다른 웨이브를 비교하게 되어 표의 차이가 실력인지 운인지 알 수 없다.
웨이브 생성 스트림과 정답/오답 스트림을 분리했다.

## 2. 적응형 출제

v7은 학기 전체 풀(2,400~2,800문항)을 셔플해 pop 하는 게 전부였다.

| 지표 | v7 | v8 |
|---|---|---|
| 약점 유형 출제 빈도 | 1.00배 (가중 없음) | 2.23배 |
| 웨이브 1~10 → 21~30 평균 난이도(t) | 1.89 → 1.87 (하락) | +0.80 이상 (8학기 전부) |
| 단원 메타데이터 | 없음 | 20,763문항 전부 태깅 |

`problemSelector.js`: 약점 유형 가중(상한 3배, 표본 4문제 미만은 판정 보류) +
웨이브별 난이도 램프 + 같은 단원 연속 방지.

⚠️ **약점을 "더 자주" 낼 뿐 "더 어렵게" 내지 않는다.** 약점 가중과 오답 페널티
강화를 같이 걸면 도움이 가장 필요한 아이가 가장 많이 맞는 역설이 된다.

**모든 신설 게이트는 수정 전 코드에서 실패하는 것을 확인했다**(비어 있지 않은 게이트).

⚠️ 게이트 작성 시 반복해서 밟은 함정:
- `mathcastle:howto`는 `{never:true}`여야 한다. `{hide:true}`는 무시돼 모달이 뜬 채로
  남고, 그러면 클릭이 막혀 **게임에 진입조차 못한 화면**을 측정한다(qa-privacy가 그랬다).
- 터치 타깃은 `isMobile`+`hasTouch` 에뮬레이션으로 재야 한다. 데스크톱 뷰포트로 재면
  `pointer: coarse` 규칙이 적용되지 않아 늘 통과한다.
- 발사체는 수백 ms 만에 사라진다. 1초 폴링으로는 못 본다 — 페이지 안에서 매 프레임 표본.
- 타워를 아무 타일에나 지으면 사거리에 몬스터가 안 들어와 "발사체 0개"인 헛검사가 된다.
- `qa-perf`의 argv[2]는 포트가 아니라 **CPU 스로틀 배율**이다.
- chrome-headless-shell 프로세스가 쌓이면 뒤이은 게이트가 무더기로 실패한다
  (제품 회귀로 오인하기 딱 좋다). qa-all.sh가 스크립트 사이에서 정리한다.
